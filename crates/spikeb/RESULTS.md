# Spike B results: bytes of process memory per key, 10,000,000 keys

Generated by `spikeb --all --n 10000000` (release build, one fresh process per
configuration, run sequentially). Keys are 16 bytes; TTL is an 8-byte absolute
expiry. Bytes per key = (memory after load - memory just before load) / n.

## Machine and measurement caveats

- Windows 10 Pro (10.0.19045), 8 cores, ~17 GB RAM, other workloads may have been running.
- The numbers are **Windows working set** (`WorkingSetSize`) and **private bytes**
  (`PrivateUsage`, committed) from `K32GetProcessMemoryInfo`. They are NOT Linux RSS.
  Do not put them next to a Valkey measurement from Linux without re-running this
  binary on Linux (the `/proc/self/status` path compiles but was not run here).
- The pointer layout uses the Windows process heap (16-byte granularity, 8-byte
  block header). glibc or jemalloc would round differently, so its absolute numbers
  are Windows-specific; the compact layout hardly depends on the allocator.
- "Pointer" is an approximation of the Redis dict, not Redis itself: no robj header,
  no embedded-string optimisation, and a blocking (not incremental) rehash.
- "Peak WS" is `PeakWorkingSetSize` since process start, so it includes index
  growth transients (old and new arrays alive together during a rebuild).
- Verification after the load: full pass over all 10M keys (value and expiry), 10,000
  never-inserted keys and one bit-flipped live key all return None. All 16 runs passed.

## Layouts byte by byte

### compact

Index slot, 8 bytes (little-endian u64):

| bytes | field |
|---|---|
| 0..4 | ref = `((chunk << 18) \| (offset / 4)) + 1` (never 0, never 0xFFFFFFFF) |
| 4..8 | tag = low 32 bits of xxh3-64(key) |

Whole slot `0` = empty, whole slot `u64::MAX` = tombstone. Addressable: 16,382
chunks x 1 MiB = ~16 GiB (error `Full` beyond that).

Record (4-byte aligned, rounded up to a size class):

| bytes | field |
|---|---|
| 0 | klen (u8, max 255) |
| 1 | flags (bit 0 = has expiry) |
| 2..4 | vlen (u16 LE, max 65535) |
| 4..4+klen | key |
| then vlen bytes | value |
| last 8 bytes, only if flag | expiry (u64 LE, unaligned) |

Record size = 4 + klen + vlen (+ 8). So 16-byte key: 20 + vlen (+ 8).
Size classes: every 4 bytes up to 128, every 8 up to 256, then 4 classes per
doubling up to the 65,802-byte maximum record. Slab = 1 MiB chunks, one size class
per chunk, bump allocation plus a per-class free list through the first 4 bytes of
a freed record. Chunks are never returned to the OS.

Index: linear probing, position = `(hash * capacity) >> 64` (capacity is any
integer). Max load (live + tombstones) = 80%. When reached: if more than 70% of
slots are live, grow x1.5, else rebuild at the same size to purge tombstones.
Rebuild rehashes from the stored keys (one record read per entry) and the old array
is freed before the call returns, so nothing is double counted after load. A removal
whose next slot is empty marks the slot empty (and the tombstones just before it)
instead of leaving a tombstone.
Load factor at the end of the 10M load: **0.6513** (15,354,379 slots, 122.8 MB,
12.28 B/key). This depends on where the 1.5x growth ladder happens to land at 10M:
it ranges from 0.533 (just after a growth, 15.0 B/key) to 0.80 (just before, 10.0 B/key),
so +-2.5 B/key of the compact overhead is a property of the chosen n.

### pointer

- Main dict: power-of-two `*mut Entry` bucket array (8 B each), chained, doubles at load 1.0 (16,777,216 buckets at 10M = 13.4 B/key).
- `Entry` = 24 B heap block: `next` (8), `key` (8, to key blob), `val` (8, to value blob). Windows heap makes it a 32 B block.
- Key blob and value blob: separate heap blocks `[u32 len][bytes]`; with 16-byte keys this is 20 B (32 B block).
- TTL: second dict (like Redis `expires`): another bucket array plus a 24 B entry `{next, key (shared main key blob), expiry}` per key.

## What the numbers suggest

- Compact stores a key in 16.6-17.0 B above the theoretical minimum for every value
  size from 8 to 100 bytes, with or without TTL: 4 B record header + ~12.3 B index
  slot share (at 65% load), size-class rounding costing 0. Pointer layout costs 74-78 B
  above the minimum without TTL and 112-116 B with it (the expires dict adds ~45 B/key).
  Compact needs 40%-64% less memory than pointer in these runs (e.g. 64.7 vs 126.2 B/key at vlen 32,
  140.99 vs 235.91 at vlen 100 with TTL).
- TTL costs exactly 8.0 B/key in compact (embedded) versus 45.6 B/key in pointer.
- Embedding threshold: this spike only built the embedded layout, so it cannot show
  a crossover; there is no separate-allocation compact variant to compare against.
  What it does show: embedding is flat at ~16.7 B overhead up to 100 B values, and only
  vlen 128 gets worse (20.6 B) because the 148-byte record rounds up to the 152-byte class
  (the 8-byte class step starts above 128). Memory alone gives no reason to stop embedding
  below ~128 B. Any real cutoff would come from non-memory costs not measured here
  (copying the whole record on overwrite that crosses a class, free-list fragmentation
  with many size classes, larger values making rebuilds' key reads touch more cache lines).
  For a data-driven threshold, a variant with an out-of-line value would need to be measured too.
- Load time (release, includes growth rebuilds): compact 5.1-7.4 s, pointer 9.1-10.0 s without TTL
  and 16-18 s with. Not tuned.
- Peak WS exceeds the final WS only slightly for compact (e.g. +3.4 B/key at vlen 8, +1.9 at vlen 16),
  from the index rebuild transient.
